# Оптимизация API и загрузки интерфейсов

Изменения не требуют миграций или изменения пула БД. На сервере нужно обновить Python-код, `frontend/build/cabinet` и `frontend/build/miniapp`, затем перезапустить API и соответствующие frontend-сервисы.

## API

- Счётчики дашборда: 12 отдельных SQL-обращений заменены тремя агрегатами (пользователи, платежи, подписки). Формат ответа и границы дат сохранены. Четыре запроса данных графиков остаются отдельными.
- Проверка лимита покупок каталога: один GROUP BY вместо запроса на каждый ограниченный тариф. На примере 20 тарифов это 2 чтения вместо 21. Исчерпанные тарифы по-прежнему скрываются; проверка конкретного тарифа при покупке не менялась.
- История в профиле кабинета и мини-аппа получает последние 50 записей через SQL LIMIT вместо загрузки всех транзакций в Python. При совпадении дат порядок задаётся id по убыванию.
- Чтение `/status` не берёт FOR UPDATE на строку пользователя перед ожиданием Remnawave. Методы изменения подписки по умолчанию сохраняют блокировку.
- Авторизация, проверки блокировки пользователя, баланс, платежи и статус подписки не кэшируются.

## Интерфейсы

Тарифы и устройства хранятся до 30 секунд в памяти текущего экземпляра кабинета/мини-аппа. Вкладки «Купить» и «Бонусы» используют один запрос тарифов. Одновременные запросы одного ресурса объединяются. Ручное обновление и успешные действия пользователя очищают кэш. Поздний ответ старого запроса не может восстановить данные после сброса. Данные не сохраняются в localStorage и не разделяются между экземплярами аккаунта.

В кабинете фоновое обновление показывает небольшой индикатор, сохраняя содержимое страницы. Мобильная раскладка проверена на ширине 390 px.

## Проверки

```powershell
$env:LUNET_TESTING='1'
.venv/Scripts/python.exe -m unittest discover -s tests -p test_api_performance.py -v
node --test tests/read-cache.test.mjs
node tests/account-navigation-smoke.mjs
npm run build --workspace lunet-cabinet --workspace lunet-miniapp --prefix frontend
```

SQL-тесты работают на локальной SQLite с настоящими моделями и проверяют результаты, число запросов, ограничения тарифов и изоляцию истории пользователей. Браузерная проверка использует локальные fixtures; запросы покупок и платежей на рабочий сервер не выполняются. Измерения задержек и нагрузочные тесты рабочего PostgreSQL/Remnawave не проводились, поэтому процент ускорения не заявляется.

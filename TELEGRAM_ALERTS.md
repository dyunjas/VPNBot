# Уведомления об ошибках и доступе к API

Используются существующие `ERROR_REPORT_BOT_TOKEN`, `ERROR_REPORT_CHAT_ID`, `ERROR_REPORT_TOPIC_ID` и Telegram proxy. После установки изменений требуется перезапустить процессы API, frontend и бота. Новая база или миграция не нужна.

- Сетевые и обычные ошибки собираются в одну сводку раз в 120 секунд. В сообщении — количество по категориям и период UTC, в приложенном TXT — источники, до трёх примеров на группу, первый traceback и до пяти IP для событий безопасности.
- Критические ошибки отмечены 🚨 и жирным заголовком; приходят сразу со звуком. Критическими считаются уровень CRITICAL, `extra={"incident_critical": True}`, сбой подключения/инициализации БД и сообщение о падении бота/запуска приложения. Обычный timeout сам по себе не критический.
- Повторы одного критического сбоя объединяются, интервал — минимум 300 секунд, с отправкой в ближайшую сводку. Не более трёх новых немедленных критических уведомлений за 120 секунд; остальные попадают в сводку. Сводки отправляются без звука.
- Повторяющиеся сетевые ошибки группируются по источнику и контексту. Различающиеся адреса, числовые ID и UUID не создают отдельное уведомление для каждого события.
- Отслеживаются отказы доступа к `/api/admin/*`, `/api/users/*`, `/api/bot/*`, запросы к платёжным и Remnawave webhook с ошибкой, попытки доступа к `.env`, `.git`, wp-admin, phpMyAdmin, actuator и другим служебным путям. Это события отказа или сканирования, а не доказательство взлома.
- Успешные запросы, обычный GET `/api/admin/auth/me` с истёкшей сессией и штатный запрос повторного TOTP не создают уведомлений. Прокси frontend не дублирует события, уже обработанные API. Роли и CSRF продолжают проверяться как раньше.
- В отчёты безопасности не включаются query, тело, cookies и заголовки авторизации. IP берётся из ASGI client, а не напрямую из X-Forwarded-For. Для правильных IP за прокси нужно корректно настроить доверенные прокси Uvicorn.
- Маскируются пароли, токены, Telegram initData, JWT, Telegram bot tokens и credentials в URL, включая traceback. Полные исходные записи продолжают обрабатываться существующей файловой системой логов.

Настройки `.env` (необязательные):

```dotenv
ERROR_REPORT_BATCH_SECONDS=120
ERROR_REPORT_CRITICAL_REPEAT_SECONDS=300
ERROR_REPORT_MAX_GROUPS=200
```

Очередь — до 500 событий, детализация — до 200 групп за период. При превышении лимита в сводке выводится счётчик, без создания отдельного уведомления на каждый пропуск. Ограничение размера TXT задаётся существующим `ERROR_REPORT_MAX_BYTES`.

Агрегация находится в памяти каждого процесса: при нескольких workers будет по одной сводке на worker, а не общая сводка для всех. При аварийном завершении процесса накопленный период может потеряться. Ошибка доставки в Telegram записывается только в `logs/error_reporter.log`, без рекурсивных уведомлений; автоматической повторной отправки нет. Уведомления не заменяют долговременные логи.

Проверки без отправки сообщений в Telegram:

```powershell
$env:LUNET_TESTING='1'
.venv/Scripts/python.exe -m unittest discover -s tests -p test_incident_reporting.py -v
```
